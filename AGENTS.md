# Challenge Buddy — работа агента

## Персонализация и область

- Общайся и составляй отчёты на русском. Технические имена следуют проекту.
- Выполняй текущий запрос до проверенного результата. Не переходи к другим дням и не считай Tasks очередью работ. Текущая учебная задача — День 3.
- Самостоятельно решай обратимые вопросы в согласованной области. Спрашивай, когда отсутствующая информация существенно меняет результат; согласованное действие не требует повторного согласования.
- Аргументированно возражай при ошибке или риске, предлагай конкретную альтернативу. Избегай несвязанных улучшений.
- Кратко сообщай о существенных находках. Разделяй наблюдение, вывод и предположение; не объявляй непроведённую проверку успешной.
- Не разворачивай изменения на VPS, не публикуй секреты или реальные пользовательские данные. Проверки выполняй с синтетическими данными и отдельными БД.

## Обязательный контекст

Перед работой явно прочитай [сжатые правила проекта](docs/agent-project-rules.md) и инструкцию выбранного профиля. Произвольные Markdown-файлы автоматически не загружаются.
Исторические результаты в evidence/day-01 не переписывай ради текущего результата.

## Выбор профиля

Явно заданный профиль имеет приоритет. Иначе выбирай по цели запроса и кратко объявляй выбор без обязательного вопроса о подтверждении.

| Профиль | Когда | Процесс и инструкция |
|---|---|---|
| Bug Fix | Ошибка, регрессия, неверный ввод или поведение | Воспроизвести → установить причину → минимально исправить → проверить сценарий и регрессии → отчёт. [Инструкция](docs/agent-profiles/bug-fix.md) |
| Research | Вопрос об устройстве проекта, связях, покрытии | Вопрос → источники → путь исполнения → проверка выводов → ответ со ссылками. [Инструкция](docs/agent-profiles/research.md) |

Research не переходит к исправлениям самостоятельно. Новую функциональность не переименовывай в баг ради применения профиля: установи область и используй общие правила и подходящие скиллы.

## Субагенты

- Делегируй при прямом запросе или применимом указании проекта. Для проверки профилей Дня 2 используй отдельный контекст исполнителя на каждый измеряемый запуск; не создавай пользовательских чатов.
- Передавай цель, исходный запрос, профиль и путь, критерии приёмки, базовую версию, разрешённые файлы, ограничения и место доказательств. Между стадиями передавай краткий результат и причину повторения.
- Исполнитель явно читает применимые инструкции. При измерении передавай симптом и требования, без готового диагноза или патча.
- Не более двух рабочих субагентов одновременно; исключай запись в одни файлы. Исследователь получает стабильный код до мутаций.
- Рекурсивное делегирование запрещено без отдельного указания. Модель и параметры наследуются, если пользователь не выбрал иные.
- Исполнитель возвращает результат, файлы, команды с exit code, доказательства и ограничения. Основной агент проверяет интеграцию и отвечает за итог.
- Независимый проверяющий читает зафиксированный результат без правок. После его ревью измеряемую генерацию не исправляй; замечания сохраняй отдельно.

## Проверки и завершение

- Для задачи проверки после изменения или обновления PR используй [два уровня](docs/testing.md): полный check → [UI smoke](docs/smoke-scenarios.md) через расширение Chrome → единый отчёт. Без доступного браузера UI отмечается BLOCKED. После новой функции актуализируй затронутые сценарии перед прогоном. Не создавай PR, деплой или расписание только ради проверки.
- Новые снимки, скриншоты, DOM и подробные логи сохраняй только в игнорируемом `test-results/current/`. Новый `check`/`test` очищает прежний прогон; повторы внутри него выполняй через `check:code`/`test:unit`, сохраняя все попытки до следующего запуска. Перед очисткой сохрани компактный текстовый итог; не создавай новые каталоги evidence для каждого запуска. При отказе безопасной очистки не применяй широкое удаление.
- Используй существующие команды и инструменты. После изменения кода — ./scripts/pnpm.sh check и самостоятельная проверка поведения. Для UI наблюдай результат в доступном реальном браузере.
- При изменениях API, безопасности и UI применяй соответственно api-and-interface-design, security-and-hardening, frontend-ui-engineering, сохраняя архитектуру проекта.
- Перед измеряемым запуском фиксируй запрос, версию профиля, базовую версию и приёмку. Сохраняй все попытки, команды, stdout/stderr и exit code. Ожидаемое падение воспроизведения отделяй от проверки исправления.
- Автономный запуск без подсказок и успех первого решения без переделки оценивай отдельно. Неудача остаётся неудачей после повтора; ограничения sandbox фиксируются отдельно.
- Итог: результат, изменённые файлы, выполненные команды и результаты, применение скиллов, ограничения и артефакты. Доработки профилей описывай отдельно; при отсутствии так и пиши.
