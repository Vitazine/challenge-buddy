# Challenge Buddy — правила проекта, v1

## Область работы

Telegram Mini App для личных ежедневных челленджей. Выполняй только текущую задачу Дня 1. Материалы `Tasks/Day 2.rtf` — `Day 5.rtf` не являются очередью работ. Не разворачивай изменения на VPS. Не добавляй восстановление из архива, напоминания, группы, новые инструменты тестирования или зависимости без необходимости текущей задачи.

## Стек и запуск

- Node.js 24, pnpm 11.25.0; TypeScript strict, ES modules.
- React 19, Vite 7, обычный CSS; Fastify 5, Zod 4, `node:sqlite`.
- Тесты: `node:test` и `node:assert/strict`, запуск через tsx.
- `./scripts/pnpm.sh dev` — локальная разработка; `./scripts/pnpm.sh check` — типы, линтер, тесты, сборка.
- Отдельные проверки: `./scripts/pnpm.sh typecheck`, `lint`, `test`, `build`.
- Если tsx не может создать IPC-сокет из-за sandbox EPERM, это ограничение среды. Сохрани сообщение и запроси штатное разрешение на запуск проверки либо используй эквивалентный `node --import tsx --test tests/*.test.ts`. Не меняй код ради обхода ограничений среды.

## Структура и архитектура

Путь запроса: React → `src/api.ts` → маршрут `server/app.ts` → `ChallengeService` → `ChallengeRepository` → SQLite.

- `src/components/`: представление, доступные элементы управления; данные и операции через props.
- `src/hooks/useChallengeApp.ts`: состояние экранов, загрузка, блокировка повторного сохранения, Telegram BackButton.
- `src/api.ts`: HTTP, заголовки входа, таймаут, единое представление ошибок.
- `server/app.ts`: Zod на входе, подтверждённый владелец, HTTP-статусы; не бизнес-правила.
- `server/challenges.ts`: правила, серверная дата и представление челленджа. Часы передаются зависимостью для воспроизводимых тестов.
- `server/repository.ts`: схема, параметризованный SQL, хранение. Существующие данные должны сохраняться при изменении схемы.
- `shared/contracts.ts`: общие типы и схемы; `shared/dates.ts`: календарные функции.
- `tests/`: API, предметная логика, авторизация. Используй существующие helpers.
- `docs/architecture.md` и README: фактический контракт и описание приложения, обновляй при изменении поведения.

## Стиль и именование

- Компоненты и классы — PascalCase; функции, поля, переменные — camelCase; хуки — `use…`.
- Имена файлов следуют соседним: `ChallengeDetail.tsx`, `challenges.ts`, `api.test.ts`.
- Двойные кавычки, точки с запятой, два пробела, форматирование Prettier.
- Именованные экспорты; `import type` для типов. Сохраняй локальный порядок импортов: внешние, shared, внутренние.
- Ошибки неизвестного происхождения сужай из `unknown`. Новый код не должен расширять небезопасные приведения типов.
- Числовой прогресс, доступность отметки, локальная дата и срок приходят с сервера. UI лишь отображает их.
- Русские пользовательские тексты; технические идентификаторы на английском.
- Сохраняй существующие зелёные/лаймовые CSS-переменные, классы и адаптивность. Семантические кнопки, видимые подписи, состояния загрузки/ошибки/пустого списка, блокировка действий во время сохранения.

## Пять примеров из исходного проекта

### 1. Валидация и тип из одной схемы — shared/contracts.ts

```ts
export const createChallengeSchema = z
  .object({
    title: z.string().trim().min(1, "Добавьте название").max(80, "Не более 80 символов"),
    startDate: dateSchema,
    duration: z.number().int().min(1).max(30),
    timeZone: z.string().max(100).refine((value) => {
      try {
        new Intl.DateTimeFormat("en", { timeZone: value });
        return true;
      } catch {
        return false;
      }
    }, "Неизвестный часовой пояс"),
  })
  .strict();
export type CreateChallengeInput = z.infer<typeof createChallengeSchema>;
```

Фрагмент сохранён с сокращённым форматированием. Повторяй единый источник типов и валидации, ограничения и запрет лишних полей.

### 2. Тонкий HTTP-обработчик — server/app.ts

```ts
api.post("/challenges", async (request, reply) => {
  const challenge = service.create(
    owners.get(request)!,
    createChallengeSchema.parse(request.body),
  );
  return reply.code(201).send(challenge);
});
```

Владелец берётся из существующего слоя входа, сервис получает проверенный ввод.

### 3. Проверка владельца и единая ошибка — server/challenges.ts

```ts
get(ownerId: string, id: string): Challenge {
  const record = this.repository.find(id, ownerId);
  if (!record) throw new AppError(404, "NOT_FOUND", "Челлендж не найден.");
  return this.present(record);
}
```

Чужой и отсутствующий объект одинаково недоступны. HTTP-ответ формирует общий error handler.

### 4. Параметризованный SQL — server/repository.ts

```ts
find(id: string, ownerId: string): ChallengeRecord | undefined {
  return this.db
    .prepare("SELECT * FROM challenges WHERE id = ? AND ownerId = ?")
    .get(id, ownerId) as unknown as ChallengeRecord | undefined;
}
```

SQL остаётся в repository, значения передаются отдельно, выборка ограничена владельцем. Приведение в этом существующем адаптере не является разрешением на произвольные касты в новом коде.

### 5. Предметные утверждения и фиксированное время — tests/domain.test.ts

```ts
test("future challenge cannot be checked in", () => {
  const repository = new ChallengeRepository(":memory:");
  const service = new ChallengeService(repository, () => now);
  const challenge = service.create("42", {
    ...challengeInput,
    startDate: "2026-10-25",
  });
  assert.equal(challenge.status, "upcoming");
  assert.throws(() => service.checkIn("42", challenge.id, true), /вне срока/);
  repository.close();
});
```

Повторяй наблюдаемое поведение, изолированную БД и управляемые часы.

## Пять антипаттернов

1. `any`, `@ts-ignore`, отключение линтера/тестов ради зелёной проверки.
2. `ownerId` из тела запроса или доверие Telegram `initDataUnsafe`; владелец определяется только существующей серверной авторизацией.
3. SQL в React, HTTP-маршрутах или сервисе; интерполяция пользовательских значений в SQL.
4. Дублирование вычислений срока, прогресса и разрешений в UI и сервере; клиентская проверка как единственная защита.
5. Секреты/реальные initData в коде, логах или артефактах; отладочный `console.log` в продуктовом коде; чтение или изменение рабочей базы ради тестов.

## Шаблоны типичного файла

Компонент: импорты типов/локальных компонентов → интерфейс props → именованная функция → вычисления для отображения → семантический JSX. Fetch и бизнес-правила остаются в своих слоях.

Сервис/репозиторий: импорты → типы → именованный класс → зависимости в конструкторе → небольшие методы. Сервис выбрасывает `AppError`, репозиторий работает с SQLite.

Тест: импорты `node:test`/assert → helpers → сценарий → подготовка → действие → утверждения → закрытие ресурсов через `t.after`, когда это уместно. Проверяй последствия, а не текст реализации.

## Скиллы, субагент и завершение

Для текущей задачи прочитай и примени `api-and-interface-design`, `security-and-hardening` и `frontend-ui-engineering` из каталога доступных скиллов. Сохраняй архитектуру этого проекта при выборе общих рекомендаций скилла. Общие предпочтения экспериментального профиля передаются отдельно и одинаково в обоих запусках.

Сначала реализуй задачу, затем запусти существующий check и самостоятельную проверку затронутого поведения. Внешний проверяющий субагент отдельно оценит зафиксированный результат; не исправляй его после внешнего ревью в рамках этой генерации. Не создавай новых пользовательских чатов и не переходи к другим дням.
