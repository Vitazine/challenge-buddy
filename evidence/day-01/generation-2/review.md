## Замечание P2: переход к созданию во время загрузки оставляет фоновые обновления деталей отключёнными

**Файлы и строки:**

- `/private/tmp/advent-day01/generation-2/src/hooks/useChallengeApp.ts:131–136` — `navigate()` инвалидирует незавершённый `load()`, но сохраняет `loading=true`.
- Тот же файл, строка **32** — устаревший ответ сразу выходит, не достигая `setLoading(false)` на строке **42**.
- Тот же файл, строка **85** — фоновый `refresh()` при `loading=true` пропускает запрос; результат создания на строках **164–166** это состояние не сбрасывает.
- `/private/tmp/advent-day01/generation-2/src/components/Dashboard.tsx:73–75` — переход к созданию доступен при сохранённой session даже во время загрузки списка: кнопка блокируется только по `ready`.

**Сценарий воспроизведения:**

1. Открыть загруженный обычный список с 21 челленджем; session уже установлена.
2. Перейти на страницу 2 и задержать её ответ API.
3. Пока список загружается, нажать «Новый челлендж».
4. Завершить старый запрос страницы 2, затем успешно создать челлендж.
5. На экране созданного челленджа дождаться таймера обновления либо возврата приложения в foreground.

`navigate()` увеличил `requestVersion`, поэтому старый запрос не снимает `loading`. Успешный `create()` показывает детали, сохраняя `loading=true`. Каждый следующий `refresh()` выходит до `api.get()`. Состояние исправляется после возврата к списку и успешной загрузки.

**Последствия:** детали перестают получать актуальные серверные `today`, `status`, `canCheckIn`, прогресс и внешние изменения до выхода из деталей. В частности, предполагаемая кодом актуализация после смены суток не работает в этом сценарии. Серверная проверка прав и запрет отметок в архиве сохраняются; потери данных этим тестом не обнаружено.

**Доказательство:** сценарий выполнен детерминированным стендом исходного `useChallengeApp.ts` с управляемыми Promise API и минимальным планировщиком hooks/effects. После успешного создания получено `view.type === "detail"`, `loading === true`, после срабатывания фонового таймера — **0 запросов GET деталей**. Проверки assertions прошли, вывод содержит `REPRODUCED`.

Это фактическое исполнение логики хука в синтетическом стенде, **не браузерная проверка и не запуск полного React renderer**. Достижимость из интерфейса дополнительно установлена статически по `Dashboard.tsx:73`. В исходном HEAD `load()` снимал loading через `finally`, а новая проверка версии запроса добавила ранний выход; это регресс изменения, а не перенесённое замечание к исходному проекту.

**Направление исправления:** согласовать инвалидирование запроса с владельцем loading-состояния либо блокировать переход к созданию до окончания загрузки; добавить регрессионный сценарий. Код в рамках ревью не исправлялся.

## Контракт, безопасность и хранение

Следующие выводы опираются на независимо выполненные существующие тесты и проверку соответствующего кода:

- **Архив отдельно от status:** `/private/tmp/advent-day01/generation-2/shared/contracts.ts:52` содержит nullable `archivedAt`; `/private/tmp/advent-day01/generation-2/server/challenges.ts:23–32` запрещает отметку по архивному признаку, сохраняя календарные статусы. Тесты проверяют active/upcoming/finished, историю и прогресс.
- **Владелец:** `/private/tmp/advent-day01/generation-2/server/app.ts:155–157` получает владельца из прежнего слоя авторизации, не из тела. `/private/tmp/advent-day01/generation-2/server/repository.ts:120` ограничивает UPDATE по id и ownerId, `/private/tmp/advent-day01/generation-2/server/challenges.ts:53–56` предварительно требует доступ к объекту. API-тест подтвердил одинаковый 404 для чужого и отсутствующего объекта, 401 без входа, 422 при попытке передать ownerId. Архивные детали и список другого владельца недоступны.
- **PUT/DELETE отметок:** `/private/tmp/advent-day01/generation-2/server/challenges.ts:58–74` проверяет архив до календарного разрешения. Тесты подтвердили 409 CHALLENGE_ARCHIVED для обоих методов владельца, 404 для чужого пользователя и неизменность истории/прогресса после отказов.
- **Идемпотентность архива:** `/private/tmp/advent-day01/generation-2/server/repository.ts:120` использует COALESCE; повтор с изменёнными часами сохраняет первый archivedAt. Тест сравнивает полный ответ первого и повторного архивирования.
- **Пагинация:** `/private/tmp/advent-day01/generation-2/server/repository.ts:94` и `:107` имеют одинаковый фильтр архива и владельца. Тест с 21 архивной и 2 обычными записями подтвердил total, размеры страниц 20+1, отсутствие дублей и разделение списков. Строгий query schema отклоняет неверные/дублированные archived и неизвестные поля.
- **Новая база:** `/private/tmp/advent-day01/generation-2/server/repository.ts:17–52` читает версию прежде DDL, создаёт схему v2 транзакционно, INSERT перечисляет поля. Файловый тест прошёл.
- **Существующая v1:** транзакционный ALTER ADD COLUMN сохраняет записи, отметки и индекс; файловый тест подтвердил данные, прогресс и user_version=2.
- **Повторное открытие v2:** два открытия с архивированной записью и историей прошли без повторного ALTER и изменения представления.
- **Будущая v99:** отказ происходит до DDL и journal_mode, соединение закрывается в catch. Тест подтвердил неизменность байтов файла, sqlite_master, версии и синтетической записи.

Новых зависимостей, изменений auth/CORS/rate limit или новых внешних интеграций в diff нет. SQL остаётся параметризованным в repository, представление данных — в сервисе, общая валидация — на HTTP-границе. Сценариев IDOR или обхода архивного запрета в проверенном изменении не найдено.

## Стиль и достаточность тестов

Стиль продуктового кода соответствует существующим соглашениям: именованные экспорты, типизированные props, функции состояния в хуке, представление в компонентах, русские тексты, прежние зелёные/лаймовые CSS tokens, семантические кнопки и `aria-pressed`. TS/TSX/CSS прошли Prettier, ESLint и типы. Присутствуют небольшие изменения форматирования незатронутого error handler, но они не меняют поведения. Несоответствие Markdown Prettier существовало в HEAD; отдельным дефектом генерации оно не считается.

Пять новых тестов `tests/archive.test.ts` содержательны: проверяют наблюдаемый API и последствия в файловой SQLite, а не текст реализации; используют синтетические данные, фиксированные часы и cleanup. Покрытие серверного контракта для этой задачи достаточное и включает важные негативные сценарии, оба метода отметок и защиту неизвестной схемы. Частичный пробел — нет автоматического сценария PUT/DELETE архива одновременно для upcoming и finished, однако общий guard расположен до календарного guard; отдельной ошибки здесь не выявлено.

Покрытие асинхронного UI в самой генерации недостаточное: `tests/*.test.ts` не исполняют хук, а заявленная автором визуальная проверка не воспроизводила задержанные ответы. Изолированный стенд ревью подтвердил важные положительные сценарии и выявил P2, отсутствующий в тестах. Для профилактики нужен тест жизненного цикла loading при навигации во время незавершённой загрузки; новые UI-зависимости для этого ревью не устанавливались.

## Границы доказательств

Независимо проверены типы, линтер, 15 серверных/предметных тестов, форматирование и сценарии логики хука в синтетическом планировщике. Полный React renderer, DOM, визуальная адаптивность, реальные сетевые задержки, Telegram BackButton, клавиатура и screen reader в этом ревью **не проверялись**. Их статическое наличие не считается результатом UI-теста. Стенд не моделирует все особенности React concurrent rendering и StrictMode. Рабочая БД, реальные Telegram-данные, VPS и другие генерации не использовались.

Скиллы применены к проверке общего контракта и идемпотентности (`api-and-interface-design`), границ доверия и доступа владельца (`security-and-hardening`), разделения компонентов/состояния, навигации и асинхронных состояний (`frontend-ui-engineering`). Полный release/security/WCAG-аудит не заявляется.
