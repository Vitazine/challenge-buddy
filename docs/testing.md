# Два уровня проверки

## После изменения или обновления PR

Агент читает AGENTS.md и сжатые правила, определяет изменённую версию
(commit и хеши незакоммиченных файлов). Артефакты текущего прогона находятся
только в игнорируемом `test-results/current/`, без новых каталогов внутри evidence.
PR используется как повод запуска в той же рабочей сессии; создание/публикация
PR не требуется. Не отправлять комментарий в PR без запроса пользователя.

1. При новой функциональности сверить требования с `docs/smoke-scenarios.md`,
   добавить или обновить затронутые сценарии и unit/integration проверки.
   Не менять ожидаемый результат только ради зелёного статуса.
2. Выполнить `./scripts/pnpm.sh check`: команда автоматически очищает прежний
   управляемый каталог `test-results/current/`, затем запускает typecheck, lint,
   все тесты и build. `./scripts/pnpm.sh test` также начинает новый чистый прогон.
3. Запустить изолированный smoke-стенд, пройти все пять сценариев расширением
   Chrome, сохранить скриншот и DOM каждого шага в `test-results/current/screenshots/`.
   Доступность расширения
   проверить до UI-прогона; при отсутствии писать BLOCKED, а не PASS.
4. Сопоставить DOM, визуальный результат, console и статусы HTTP.
   Не сохранять headers/body с credentials. При падении указать шаг,
   ожидаемое/фактическое и предполагаемый слой: UI → api → app → service → repo.
5. Остановить стенд и собрать единый отчёт. Общий PASS возможен только при
   успешных двух уровнях на одной версии кода. Если версия изменилась между
   уровнями, повторить затронутые проверки на конечной версии.

Для измеряемого запуска с полными логами подготовить каталог **до открытия лога**,
затем выполнить те же проверки без повторной очистки:

```sh
./scripts/pnpm.sh test:prepare
./scripts/pnpm.sh exec node scripts/testing/run-command.mjs test-results/current/logs/check-01 ./scripts/pnpm.sh check:code
./scripts/pnpm.sh exec node scripts/testing/run-command.mjs test-results/current/logs/smoke-01 ./scripts/pnpm.sh exec node --import tsx scripts/testing/smoke-server.mjs
```

Внутри одного прогона каждый префикс новый (`check-02`, `smoke-02` при повторе);
перезапуск smoke-стенда не очищает предыдущие попытки. `.json` хранит отдельно stdout/stderr и exit code,
`.log` — поток вывода. Для остановки стенда Ctrl+C; при фоновом запуске
послать SIGTERM именно его процессу, дождаться завершения и записи лога.
При sandbox IPC EPERM сохранить неуспех и использовать штатное разрешение;
не изменять npm scripts ради ограничений среды.

Перед следующим новым прогоном прежние изображения, DOM и подробные логи
из `test-results/current/` удаляются. Сначала сохранить компактный итог с
командами, exit code, первым FAIL и результатом повторов в текстовом отчёте.
В Git остаются тесты, сценарии, инструкции и такие отчёты; изображения и
ZIP-снимки evidence игнорируются. В `evidence/day-02/` сохраняется только README.md,
в `evidence/day-03/` — README.md и cleanup-policy.md. Промежуточные логи, DOM,
патчи, manifest и копии исходников удалены по запросу пользователя; `.gitignore`
предотвращает повторное добавление. Для новых результатов обновлять эти итоги;
подробные данные хранить только в текущем прогоне. Новые снимки исходников создавать только в
`test-results/current/`; для долговременной версии использовать Git commit.

Ранее опубликованные снимки Дня 1 и docs/screenshots остаются в истории и
текущем индексе по ограничению области этой задачи; .gitignore предотвращает
добавление новых файлов, но сам не удаляет уже отслеживаемые. Их снятие с учёта
требует отдельного разрешения на изменение исторических материалов.

Очистка отказывается от каталогов без `.owner` и симлинков.
Она ограничена `test-results/current/`; завершённая одноразовая миграция
старых файлов удалена из инструмента. Не заменять отказ широким `rm -rf`. Работающая БД приложения
и исходные изображения вне каталога артефактов не затрагиваются.

Это локальный агентный flow. CI и расширение Chrome — разные исполнители:
`check` может исполняться CI, но UI-прогон требует активного агента с доступным
расширением. События GitHub сами этот агент не запускают; webhook, scheduler
и автоматическое комментирование не настроены.

## Готовый запрос после изменения/PR

> Выполни оба уровня проверки текущей версии Challenge Buddy по docs/testing.md:
> полный check, затем все smoke из docs/smoke-scenarios.md через расширение Chrome.
> Начни новый прогон с автоматической очисткой test-results/current, используй
> изолированную БД и синтетические данные. Не создавай новые каталоги evidence.
> Для каждого шага сохрани DOM и скриншот. Собери единый отчёт со статусами,
> командами, exit code и ограничениями. При падении укажи предполагаемое место
> проблемы; не скрывай первую попытку. Деплой и публикацию не выполняй.

## Готовый запрос после новой функции

> Я задеплоил новую фичу: <описание и критерии приёмки>. Сверь локальную версию
> с указанной версией фичи, обнови tests и docs/smoke-scenarios.md под изменённое
> поведение и прогони оба уровня по docs/testing.md. Проверяй локально на отдельной
> БД с синтетическими данными; production не изменяй. Попытки текущего прогона
> и скриншоты храни в test-results/current, компактный текстовый итог сохрани
> перед следующим прогоном. Если нужной версии локально нет, сообщи об этом.

Этот запрос подготовлен как усиление задания. Новая продуктовая функция и
деплой в рамках Дня 3 не выполняются.

## Шаблон единого отчёта

```text
Версия: commit + manifest хешей; запрос; время; сценарии версии N
Код: команда → exit code → passed/failed/skipped → ссылки на логи
Первая попытка: результат новых тестов; исправления/повторы; ограничения среды
UI: S1…S5 → PASS/FAIL/BLOCKED → каждый шаг expected/actual, DOM, screenshot
Диагностика: console, HTTP, вероятный слой и обоснование при отказе
Итог: PASS только при успехе двух уровней; непроверенные среды отдельно
Файлы, скиллы, ограничения, остановка стенда
```
