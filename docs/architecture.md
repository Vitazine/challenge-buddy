# Архитектура первой версии

## Решение

Один репозиторий и один пакет. В разработке два процесса: Vite и Fastify. В собранной версии Fastify раздает и HTML/JS/CSS, и `/api`. SQLite хранится на постоянном диске того же сервера.

Путь действия: **React-компонент → src/api.ts → HTTP-маршрут → проверка пользователя и Zod → ChallengeService → ChallengeRepository → SQLite**.

Бизнес-логика не зависит от HTTP и React. Сервер возвращает вычисленные `today`, `endDate`, `canCheckIn`, `status` и `progress`, чтобы интерфейс не решал, разрешена ли отметка. Общие типы и календарные функции находятся в shared.

## Контракт API

Все защищенные запросы: `Authorization: tma <initData>`. В локальном режиме вместо него нужен `X-Local-Development: true`, loopback-соединение и допустимый Origin, если он передан. Development-сервер нельзя публиковать через туннель.

| Метод | Адрес | Результат |
|---|---|---|
| GET | /api/health | 200, состояние процесса, без пользовательских данных |
| GET | /api/session | 200, режим авторизации |
| GET | /api/challenges?page=1&pageSize=20&archived=false | 200, items/page/pageSize/total; максимум 50 записей |
| PUT | /api/challenges/:id/archive | 200, архивный челлендж; повтор сохраняет первоначальный archivedAt |
| POST | /api/challenges | 201, созданный челлендж |
| GET | /api/challenges/:id | 200, один челлендж; 404 для отсутствующего или чужого |
| PUT | /api/challenges/:id/check-ins/today | 200, состояние после отметки; идемпотентно |
| DELETE | /api/challenges/:id/check-ins/today | 200, состояние после отмены; идемпотентно в пределах дня |

POST принимает `title`, `startDate` в YYYY-MM-DD, `duration`, `timeZone`. Владелец из тела запроса не принимается. Контракты определены в `shared/contracts.ts`.

Ошибки единообразны: `{ "error": { "code": "...", "message": "..." } }`. Статусы: 401 — нет входа; 404 — нет доступного объекта; 409 — действие вне срока; 422 — некорректные поля; 429 — ограничение частоты; 500 — внутренняя ошибка без деталей.

POST создания не идемпотентен: после сетевого таймаута нельзя автоматически повторять его. Сначала проверить список. UI блокирует повторное нажатие во время запроса; сквозной Idempotency-Key можно добавить отдельной учебной задачей. PUT/DELETE отметки рассчитывают «сегодня» заново на сервере при каждом запросе.

## Хранение

`challenges`: id, ownerId, title, startDate, duration, timeZone, createdAt.

`check_ins`: challengeId, date. Составной PRIMARY KEY запрещает дубли даже при одновременных запросах. Внешний ключ с каскадом подготовлен для будущего удаления челленджа.

Версия начальной схемы — 1. При дальнейшем изменении структуры нужны версионированные миграции; не изменять CREATE TABLE и не считать это миграцией существующей базы.

Параметризованный SQL находится только в repository. Для маленького проекта это проще ORM и сохраняет четкую границу. Отдельная таблица пользователей не нужна: приложение хранит только подтвержденный Telegram ID, не копирует имя, username, фото или initData в базу.

## Границы доверия

- Пользовательский ввод и HTTP-запросы → Zod, ограничение тела 16 KiB.
- Telegram initData → HMAC-SHA256, сравнение постоянного времени, проверка дубликатов полей и срока один час, допустимый сдвиг часов 30 секунд.
- ID объекта → запрос с одновременно заданными id и ownerId.
- База → постоянный локальный диск, не каталог публичной статики.
- Браузер → React-экранирование; нет dangerouslySetInnerHTML и клиентских секретов.
- Production → HTTPS на reverse proxy; CSP разрешает официальный Telegram SDK и embedding только Telegram Web/своим origin. X-Frame-Options заменен frame-ancestors CSP, чтобы не ломать Telegram Web.
- API → no-store для пользовательских ответов; rate limit 120 запросов/минуту на IP, один экземпляр. Перед несколькими экземплярами нужен общий limiter и пересмотр базы.

Токен бота берется из окружения. initData используется только в памяти клиента/запросе и не логируется. Челленджи и Telegram ID — персональные данные; для тестового этапа используются собственные тестовые записи. Публичный сервис требует пользовательского удаления/экспорта и политики хранения, включая резервные копии.

## Визуальное направление

Рабочая гипотеза без стороннего макета: спокойный ежедневник, теплый светлый фон, темно-зеленые действия и лаймовые отметки. Главное действие списка — создание; в деталях — отметка сегодняшнего дня. На мобильном одна колонка, на широком экране рядом с календарем показан прогресс.

Обязательные состояния: загрузка, пустой список, ошибка с повтором, ожидание сохранения, отметка, отмена, будущий/завершенный челлендж, отсутствие Telegram-входа. Формы имеют видимые подписи; календарь — текстовые статусы, не только цвет; системная кнопка Back в Telegram возвращает к списку.


## Архив челленджей (День 1)

`archivedAt: string | null` — отдельное измерение состояния. `null` означает обычный список; timestamp ISO UTC задаёт сервер при первом архивировании. `status` остаётся календарным (`upcoming | active | finished`), история и прогресс сохраняются. В архиве `canCheckIn=false`.

`GET /api/challenges` по умолчанию выбирает только неархивные записи. `archived=true` выбирает только архив; `archived=false` — обычный список. Оба фильтра применяются к `items` и `total` в пределах текущего владельца до пагинации. `page` и `pageSize` сохраняют ограничения; неизвестные параметры и значения archived, кроме строк true/false, дают 422.

`PUT /api/challenges/:id/archive` не принимает тело и возвращает актуальный Challenge. Повтор безопасен: SQL COALESCE сохраняет первый timestamp. Отсутствующий и чужой id дают одинаковый 404 NOT_FOUND; запрос без входа — 401. Архив остаётся доступен владельцу через GET деталей. PUT и DELETE `/check-ins/today` для архива дают 409 CHALLENGE_ARCHIVED независимо от календарного срока. Восстановления нет.

SQLite user_version=2: новая база создаётся в транзакции; v1 мигрирует через ALTER TABLE ADD COLUMN archivedAt TEXT без потери записей, отметок и индексов; v2 открывается без ALTER. Неизвестная будущая версия отклоняется до PRAGMA, изменяющих файл, и DDL; соединение закрывается.

UI переключает «Мои челленджи»/«Архив», сбрасывает страницу при смене вида и корректирует страницу при уменьшении списка. Детали возвращаются в исходное представление. Семантические кнопки блокируются во время сохранения. Версия запросов и отмена фонового эффекта защищают от устаревших ответов списка и деталей, включая запрос, начатый до архивирования. Пустой архив и сетевые ошибки имеют отдельные состояния.
